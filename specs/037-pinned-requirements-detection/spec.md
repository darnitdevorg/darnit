# Feature Specification: Pinned-Requirements Detection

**Feature Branch**: `037-pinned-requirements-detection`

**Created**: 2026-09-14

**Status**: Draft

**Input**: User description: "Implement issue #429 -- `repro_deps_pinned` unconditionally flags an exact-pinned `requirements.txt` as a loose manifest. The check should inspect the file's contents: if every dependency specifies an exact version or a hash, it should not report a hard failure. Reported by @Jaydeep869 while evaluating `darnit-reproducibility` against real repositories."

## Context

`repro_deps_pinned` decides whether a project's dependencies are pinned. It does this **purely by filename**: it never opens any of the files it judges.

- A recognized lock file present -> PASS at confidence 0.8.
- A "loose manifest" present with no lock file -> FAIL at confidence 0.8.
- Neither -> INCONCLUSIVE.

`requirements.txt` sits in the loose-manifest list. So a project whose `requirements.txt` reads:

```text
numpy==1.26.4 --hash=sha256:2a02aba9ed12e4ac4eb3ea9421c420301a0c6460d9830d74a9df87efa4912010
click==8.1.7 --hash=sha256:ae74fb96c20a0277a1d615f1e4d73c8414f5a98db8b799a7931d1582f3390c28
```

receives the same hard FAIL as one that reads `numpy` with no constraint at all. The message -- "Dependency manifests found but no lock files" -- is accurate about what the check looked at and misleading about what it concluded.

This is a false negative: the tool reports non-compliance for a repository that is, on the evidence, compliant. Under Constitution Principle II that is the *safe* direction of error, which is why this has not caused harm. It is still wrong, and it is the failure mode most likely to make an operator distrust the tool, because they can see with their own eyes that their dependencies are pinned.

The correction is not simply "pass when everything uses `==`". A fully `==`-pinned `requirements.txt` pins *direct* dependencies while leaving transitive dependencies to float at install time; a lock file pins the entire resolved graph. Those are genuinely different reproducibility guarantees, and collapsing them into one PASS would trade a false negative for a false positive -- the error direction the constitution actually forbids.

## Clarifications

### Session 2026-09-15

- Q: How does the version-pinned WARN get produced, given that `HandlerResultStatus` has no WARN and the only existing route to WARN discards the handler's message? -> A: Add WARN to the handler result vocabulary as a conclusive outcome carrying the handler's own message (Option A). This is a framework change in `darnit` core, additive, following the feature 036 precedent of widening `HandlerResult` rather than smuggling meaning through a fallthrough.
- Q: Where does a commit-SHA-pinned VCS reference land in the classification, given FR-010 says it counts as pinned but FR-003 defines the tiers by exact version and hash? -> A: Pinned but not hashed (Option B). It satisfies FR-010 and caps the file at version-pinned (WARN) even when every other line carries a hash.
- Q: What do non-requirement lines (`-e .`, `--index-url`, `--extra-index-url`, `--find-links`) do to the classification? -> A: Skipped (Option A). They are not requirement lines and count toward no tier; the file classifies on its requirements alone.
- Q: Does inspection cover the requirements-file family (`requirements-dev.txt`, `requirements/base.txt`) or only the exact root filename? -> A: Root `requirements.txt` only (Option A), exactly as discovered today. Widening discovery would change verdicts for repos FR-014 promises not to touch.
- Q: What confidence do the new content-derived verdicts carry, given content inspection is stronger evidence than filename matching? -> A: Keep 0.8 across all of them, matching the lock-file path. Confidence in this codebase is coarse and uncalibrated; a second scale would start a comparability argument across every control rather than settle one. Sharper confidence semantics belong with the tightness taxonomy in #415.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A fully hash-pinned requirements.txt is not reported as unpinned (Priority: P1)

A maintainer whose `requirements.txt` was generated by `pip-compile --generate-hashes` runs a reproducibility audit. Every line carries an exact version and a cryptographic hash, and the file includes the full transitive closure. The audit does not tell them their dependencies are unpinned.

**Why this priority**: This is the strongest form of pinning available in the pip ecosystem -- stronger than several of the lock files the check already passes. Reporting it as a failure is the least defensible version of the bug.

**Independent Test**: Create a repo containing only a `requirements.txt` whose every requirement line has `==` and at least one `--hash=`. Run the reproducibility audit. The control does not return FAIL.

**Acceptance Scenarios**:

1. **Given** a repo with a `requirements.txt` where every requirement line carries `==` and `--hash=`, and no lock file, **When** the reproducibility audit runs, **Then** `repro_deps_pinned` returns PASS.
2. **Given** the same repo, **When** the audit runs, **Then** the result message names hash-pinning as the reason, so the operator can tell the verdict came from reading the file rather than from its name.
3. **Given** the same repo, **When** the audit runs, **Then** the evidence records which file was inspected and what was found, so the verdict is reviewable without re-running the tool.

---

### User Story 2 - A version-pinned requirements.txt is distinguished from an unpinned one (Priority: P1)

A maintainer whose `requirements.txt` pins every direct dependency with `==` but carries no hashes runs an audit. They get WARN rather than FAIL -- the result distinguishes their repository from one using open ranges -- and the message tells them transitive dependencies are what remains unpinned.

**Why this priority**: This is the common case -- far more projects hand-maintain `==` pins than run `pip-compile --generate-hashes`. Getting only Story 1 right would fix the rare case and leave the common one broken.

**Independent Test**: Create two repos, one with all-`==` requirements and one with `>=` ranges. Run the audit against both. The first returns WARN, the second FAIL.

**Acceptance Scenarios**:

1. **Given** a repo whose `requirements.txt` pins every requirement with `==` and no hashes, and no lock file, **When** the audit runs, **Then** the control returns WARN, and the message identifies unpinned transitive dependencies as what is missing.
2. **Given** a repo whose `requirements.txt` contains any open specifier (`>=`, `>`, `~=`, `^`, `*`, or a bare package name), **When** the audit runs, **Then** the control returns FAIL and the message identifies at least one offending requirement.
3. **Given** a repo mixing pinned and unpinned lines, **When** the audit runs, **Then** the unpinned lines determine the verdict -- one floating dependency is enough to break the build's reproducibility.

---

### User Story 3 - Lock files continue to take precedence (Priority: P2)

A repository containing both a lock file and a `requirements.txt` is judged on the lock file, exactly as before this change.

**Why this priority**: Regression protection. The lock-file path is the one that currently works, and it must keep working identically. Lower priority only because it is about preserving behavior rather than fixing it.

**Independent Test**: Create a repo with both `uv.lock` and a deliberately unpinned `requirements.txt`. The audit passes on the lock file and the requirements content is not consulted.

**Acceptance Scenarios**:

1. **Given** a repo with a recognized lock file and a `requirements.txt` full of open ranges, **When** the audit runs, **Then** the control returns PASS on the lock file.
2. **Given** a repo with no dependency files at all, **When** the audit runs, **Then** the control returns INCONCLUSIVE, unchanged.
3. **Given** any repo, **When** the audit runs before and after this change with an unchanged lock-file situation, **Then** the status and confidence are identical.

---

### Edge Cases

- **Unreadable or undecodable `requirements.txt`**: the file exists but cannot be read (permissions) or is not valid UTF-8. The check cannot inspect contents, so it must not claim to have. Treat as not-inspectable and fall back to the pre-feature presence-based verdict rather than guessing in either direction.
- **Empty file, or only comments and blank lines**: there are no dependencies to pin. This is not evidence of good pinning practice, and it is not evidence of bad practice either. Resolved: treat the file as absent (FR-011).
- **`-r other.txt` / `-c constraints.txt` includes**: the file defers part of its content to another file. Following includes is out of scope for v0; a file containing an unresolved include has not been fully inspected and must not be reported as fully pinned.
- **Editable and direct-reference installs** (`-e .`, `pkg @ git+https://...@<sha>`, local paths): a VCS reference pinned to a full commit SHA is genuinely pinned but is not hash evidence, so it caps the file at version-pinned (FR-010); one pointing at a branch is not pinned at all. A bare `-e .` refers to the project itself rather than a dependency and is skipped (FR-018).
- **Environment markers and extras** (`pkg[extra]==1.0; python_version < "3.11"`): these decorate a requirement without changing whether its version is pinned. Parsing must not be confused by them.
- **`!=` exclusions and compound specifiers** (`pkg>=1.0,<2.0`, `pkg==1.*`): `==1.*` is a wildcard, not an exact pin, despite containing `==`. A naive substring check for `==` gets this wrong.
- **Non-`requirements.txt` loose manifests**: `setup.py`, `package.json`, `Cargo.toml`, and `go.mod` remain judged by presence alone. Their verdicts do not change in this feature (see Out of Scope).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: When a recognized lock file is present, the control MUST return the same status, message, and confidence it returns today. Lock files are judged first and short-circuit content inspection.
- **FR-002**: When no lock file is present and a `requirements.txt` is present, the control MUST inspect the file's contents before deciding a verdict.
- **FR-003**: The control MUST classify an inspected `requirements.txt` into one of: **hash-pinned** (every requirement carries an exact version and at least one hash), **version-pinned** (every requirement is exactly identified -- by an exact version, or by a direct VCS reference at a full commit SHA -- but at least one carries no hash), **unpinned** (at least one requirement is not exactly identified), or **not-inspectable** (contents unavailable or containing unresolved includes).
- **FR-004**: A hash-pinned `requirements.txt` MUST produce PASS. Hashes pin exact artifacts and such files are generated with the full transitive closure, so the evidence is at least as strong as the lock files this control already passes.
- **FR-005**: A version-pinned `requirements.txt` MUST produce WARN, not PASS and not FAIL. Direct dependencies are pinned but transitive dependencies resolve at install time, so the build is not reproducible and the control cannot honestly assert that it is. WARN is the Principle II answer for "we can see this is incomplete."

  The consequence is deliberate and worth stating plainly: because WARN counts as FAIL for compliance calculations, a project that pins every direct dependency still cannot reach compliance on this control without adopting a lock file. For a framework whose subject is reproducibility, that is the correct message rather than an unfortunate side effect.

  The message MUST say what is missing (transitive pinning) rather than only that the check did not pass.
- **FR-006**: An unpinned `requirements.txt` MUST produce FAIL, and the message MUST name at least one requirement that is not pinned, so the operator can act without re-deriving the finding.
- **FR-007**: A not-inspectable `requirements.txt` MUST produce the pre-feature presence-based verdict (FAIL), and the message MUST state that contents could not be inspected -- distinguishing "we read it and it is unpinned" from "we could not read it."
- **FR-008**: Version-pin detection MUST treat a wildcard such as `pkg==1.*` as NOT an exact pin.
- **FR-009**: Version-pin detection MUST correctly handle environment markers, extras, comments, blank lines, and line continuations without misclassifying an otherwise-pinned requirement.
- **FR-010**: A direct VCS reference pinned to a full commit SHA MUST count as exactly identified, so its presence alone does not produce FAIL. It MUST NOT count as hash evidence: a file containing one classifies at best version-pinned (WARN), even if every other requirement carries a hash. FR-004's PASS rests on such files being produced under a require-hashes workflow that refuses unhashed requirements and cannot hash a git reference at all; a file containing a VCS reference is not such a file and must not borrow that justification. The same reference pointing at a branch or tag MUST NOT count as exactly identified and produces FAIL.
- **FR-011**: A `requirements.txt` containing no requirement lines -- empty, or only comments and blank lines -- MUST be treated as though the file were absent. It declares no dependencies, so it is evidence of neither good nor bad pinning practice. Any other loose manifest present then decides the verdict; if there is none, the control returns the existing no-dependency-files INCONCLUSIVE.
- **FR-012**: The result evidence MUST record which file was inspected, the classification reached, and the specific requirements that drove it, so a reviewer can audit the verdict from the result alone.
- **FR-013**: Every verdict this control can now return MUST remain legible to an operator who has not read this spec -- the message states what was examined and what was concluded, not merely a status.
- **FR-014**: The feature MUST NOT change the verdict for any repository whose dependency situation is judged by a lock file, by a non-`requirements.txt` loose manifest, or by the absence of dependency files.
- **FR-015**: The feature MUST NOT introduce a new runtime dependency on any package outside the existing darnit dependency set.
- **FR-016**: The control MUST be able to conclude WARN with its own message and stop the pass chain. Today a handler can only return PASS, FAIL, INCONCLUSIVE, or ERROR; an INCONCLUSIVE continues to the next pass and the eventual WARN carries a fixed "manual verification required" string, which cannot satisfy FR-005 or FR-013. The handler result vocabulary MUST therefore gain a conclusive WARN outcome, additively, so that a handler which can see that evidence is incomplete can say so in its own words.
- **FR-017**: Adding the conclusive WARN outcome MUST NOT change the verdict of any existing handler. No handler other than `repro_deps_pinned` returns the new outcome as part of this feature, and the existing all-inconclusive WARN fallthrough MUST continue to behave as it does today for controls that never produce one.
- **FR-018**: Lines that are not dependency declarations MUST be skipped rather than classified. This covers pip option lines (`--index-url`, `--extra-index-url`, `--find-links`, and similar) and self-references such as `-e .` or a bare local path, which name the project being audited rather than a dependency. Skipped lines count toward no tier: a file whose requirements are all hash-pinned still classifies hash-pinned when it also carries `-e .` and an index option. A file containing only skipped lines has no requirement lines and is governed by FR-011.
- **FR-019**: File discovery MUST remain unchanged: the control inspects a `requirements.txt` at the repository root and nothing else. Other spellings in the requirements family (`requirements-dev.txt`, `requirements/base.txt`, and similar) are not discovered today, and this feature MUST NOT begin discovering them -- a repository whose only requirements file is one of those is INCONCLUSIVE today and MUST stay INCONCLUSIVE.
- **FR-020**: The hash-pinned PASS, the version-pinned WARN, the unpinned FAIL, and the not-inspectable FAIL MUST all carry confidence 0.8, the value the lock-file path already uses. Content inspection is stronger evidence than filename matching, but this control's confidence scale is not calibrated finely enough to carry that distinction, and introducing a second scale here would make this control's numbers incomparable with every other control's. The no-dependency-files INCONCLUSIVE keeps its 0.0.

### Key Entities

- **Requirement line**: one dependency declaration within `requirements.txt`, after comments, blank lines, and continuations are resolved. Carries a package name, an optional extras list, an optional version specifier, optional hashes, and an optional environment marker.
- **Pin classification**: the verdict reached about a single requirement line -- exactly pinned, hash pinned, or not pinned.
- **File classification**: the verdict reached about the file as a whole, derived from its lines: hash-pinned, version-pinned, unpinned, or not-inspectable. The weakest line governs.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A repository whose only dependency file is a `pip-compile --generate-hashes` output no longer receives a FAIL from `repro_deps_pinned`. Verified against a fixture reproducing the reporter's case in #429.
- **SC-002**: A repository with an all-`>=` `requirements.txt` still receives a FAIL, and the message names an offending requirement. Verified by fixture.
- **SC-003**: A repository with an all-`==` `requirements.txt` receives WARN, distinct from the all-hash PASS and the all-`>=` FAIL. Verified by fixture, comparing all three results.
- **SC-004**: A repository with a lock file present produces byte-identical control output before and after this change, including confidence. Verified by comparing results across the change for a lock-file fixture.
- **SC-005**: A repository with no dependency files produces byte-identical control output before and after this change.
- **SC-006**: Every edge case enumerated above has a fixture and an asserted verdict, including the ones where the correct answer is "we could not determine."
- **SC-007**: No new runtime dependency is introduced. Verified by checking the touched package's imports against its declared dependencies.
- **SC-008**: Adding the conclusive WARN outcome changes no existing control's status. Verified by running the full control set against the existing fixtures before and after and diffing per-control status.

## Assumptions

- The feature spans two packages. The content inspection is plugin-local to `darnit-reproducibility`, but FR-016's conclusive WARN outcome is a framework change in `darnit` core. That split is deliberate and consistent with Principle I: the plugin gains no framework privileges, the framework gains a vocabulary item that any handler may use.
- The scope is `requirements.txt` only. The other loose manifests have analogous content-inspection questions with ecosystem-specific answers, and bundling them would mean four parsers in one change.
- Content inspection reads the file from disk at audit time. There is no caching requirement; these files are small and read once per audit.
- The existing confidence value for the lock-file PASS (0.8) is treated as correct and is not revisited here, and every new verdict adopts it (FR-020). Giving content-derived verdicts a sharper confidence is deferred to the tightness taxonomy in #415, which is where confidence would gain a definition worth calibrating against.
- "Exact version" means the PEP 440 `==` operator with a complete version, excluding wildcards. `===` (arbitrary equality) also counts as exact.
- The reporter's proposed fix suggested PASS with lower confidence *or* WARN for the version-pinned case. Resolved as WARN (FR-005). A build with floating transitive dependencies is not reproducible, so WARN is substantively accurate rather than merely conservative -- and Principle II is explicit that doubt resolves to WARN. The accepted cost is that `==`-pinning projects cannot reach compliance on this control without a lock file.

## Dependencies

- PR #439 (issues #427, #428) -- until that merges, `repro_deps_pinned` does not execute at all via the CLI, so this feature cannot be verified end-to-end through `darnit audit`. Unit-level verification is unaffected.
- Issue #415 (reproducibility layer + tightness taxonomy) -- the taxonomy would supply a principled answer to "is a version-pinned requirements.txt good enough?", since the answer depends on whether the target is bit-for-bit or runs-to-completion. It is not a blocker; this feature must pick a defensible default and should be revisited when the taxonomy lands.

## Out of Scope

- **Content inspection for the other loose manifests** (`setup.py`, `package.json`, `Cargo.toml`, `go.mod`). Each needs ecosystem-specific handling, and `go.mod` in particular is questionably classified as loose at all given `go.sum`. Separate work.
- **Following `-r` and `-c` includes.** Resolving the include graph introduces path traversal and cycle concerns; v0 treats an unresolved include as not-inspectable.
- **Verifying that a lock file is current** relative to its manifest. The existing 0.8 confidence already acknowledges this gap.
- **The false-PASS siblings**: #430 (`repro_hermetic_build` misses `go install`), #431 (`repro_build_env_declared` passes on `FROM alpine:latest`), #432 (compiler flags). Those share a different root cause -- controls that pass on artifact presence rather than artifact quality -- and warrant their own treatment.
- **#433** (native C/C++ toolchain support). That is a feature addition, not a correctness fix.
- **Split requirement files.** Inspecting `requirements-dev.txt`, `requirements/base.txt`, and the rest of the family would change verdicts for repositories that have no root `requirements.txt` and are INCONCLUSIVE today. That is a discovery change, not a correctness fix, and belongs in its own work.
- **Artifact source pinning.** A custom index (`--index-url`, `--extra-index-url`, `--find-links`) changes where artifacts are resolved from, which is a genuine reproducibility concern, but it is a different question from whether versions are pinned. Treating it here would widen the control's subject without saying so. Worth raising against the tightness taxonomy in #415.
- **Remediation**. Generating a lock file for a project that lacks one is a separate action from auditing whether one exists.
